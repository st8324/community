## 1. 목적

보안, 하네스 엔지니어링(테스트 자동화), 자동배포를 직접 경험하기 위한 **학습용 프로젝트**다.
기능의 풍부함보다 "작은 기능을 안전하게 만들고, 자동으로 검증하고, 자동으로 배포하는 과정"을 익히는 것이 우선이다.

**원칙**
- 기능은 2장 "포함 범위"를 넘지 않는다. 범위 밖 기능은 명시적 요청이 있을 때만, 이 문서를 먼저 갱신한 뒤 추가한다.
- 모든 기능 요구사항은 수용 기준(AC)을 가지며, 구현 전에 AC 기반 테스트를 먼저 작성한다.

## 2. 범위

### 2.1 포함 (MVP)
1. 회원가입(가입 직후 자동 로그인) / 로그인(로그인 상태 유지 선택) / 로그아웃 (이메일 + 비밀번호) — v0.4
2. 게시글 작성 / 목록 조회 / 상세 조회 / 수정 / 삭제
3. 댓글 작성 / 삭제
4. 관리자: 게시글·댓글 삭제 권한

### 2.2 제외 (MVP 이후)
7장에 전체 목록 정리.

## 3. 사용자 역할과 권한

| 역할 | 설명 |
|---|---|
| 비회원 (GUEST) | 로그인하지 않은 사용자 |
| 회원 (USER) | 가입 후 로그인한 사용자 |
| 관리자 (ADMIN) | 배포 시 초기 시드로 생성되는 계정. 회원 권한 + 삭제 권한 |

### 3.1 권한 매트릭스

| 기능 | 비회원 | 회원 | 관리자 |
|---|:-:|:-:|:-:|
| 회원가입 | O | - | - |
| 로그인 | O | - | - |
| 로그아웃 | O (204, 지울 것 없음) | O | O |
| 로그인 연장 (리프레시 토큰, AUTH-06) | X (401) | O | O |
| 현재 사용자 조회 (로그인 상태 확인) | X (401) | O | O |
| 게시글 목록·상세 조회 | O | O | O |
| 댓글 조회 | O | O | O |
| 게시글 작성 | X | O | O |
| 게시글 수정 | X | 본인 글만 | 본인 글만 |
| 게시글 삭제 | X | 본인 글만 | **모든 글** |
| 댓글 작성 | X | O | O |
| 댓글 삭제 | X | 본인 댓글만 | **모든 댓글** |

## 4. 기능 요구사항

### 4.1 인증 (AUTH)

| ID | 요구사항 | 수용 기준 (AC) |
|---|---|---|
| AUTH-01 | 이메일·비밀번호로 회원가입한다. | ① 형식이 올바른 이메일과 정책(SEC-03)을 만족하는 비밀번호로 가입 성공 → **201, 가입 직후 자동 로그인**: 응답 본문은 AUTH-05 형태(`id`, `displayName`), 토큰 쿠키는 AUTH-02 ③과 같이 발급. 요청의 `rememberMe`(선택, 기본 false)가 true면 AUTH-06도 적용 (v0.4, D-15) ② 이미 가입된 이메일은 거부 → **409 `EMAIL_ALREADY_USED`** ③ 이메일은 대소문자 구분 없이 중복 판단 ④ 가입 직후 역할은 USER. **요청에 `role` 등 다른 필드가 있어도 무시**한다 ⑤ 이메일은 **앞뒤 공백 제거 → 소문자 변환** 후 저장·비교한다 (DATA-01) ⑥ 이메일 형식: 정규화 후 `영문·숫자·._%+-` 로컬부 + `@` + 도메인(`영문·숫자·.-`) + `.` + 영문 2자 이상, **최대 254자**. 위반 시 400 `VALIDATION_FAILED` ⑦ 비밀번호 정책(SEC-03) 위반 시 400 `VALIDATION_FAILED` |
| AUTH-02 | 이메일·비밀번호로 로그인하면 JWT를 발급받는다. | ① 정상 자격증명이면 성공 → **200**, 응답 본문은 AUTH-05와 같은 형태(`id`, `displayName`) ② 이메일이 없거나 비밀번호가 틀리면 **동일한 오류 응답** 반환 → **401 `INVALID_CREDENTIALS`** (계정 존재 여부 노출 금지. 상태코드·본문이 바이트 단위로 같아야 함) ③ 토큰은 SEC-05 방식으로 전달 ④ 이메일은 AUTH-01 ⑤와 같이 정규화한 뒤 조회한다 (대소문자 달라도 로그인 성공) ⑤ 빈 값, 이메일 254자 초과, 비밀번호 64자 또는 72바이트 초과는 400 `VALIDATION_FAILED` (이런 비밀번호로는 가입할 수 없으므로 계정 존재 여부와 무관) ⑥ **만료·변조된 토큰 쿠키가 남아 있어도 회원가입·로그인은 정상 처리**한다 (해당 요청에서는 토큰 쿠키를 읽지 않음) ⑦ 토큰 클레임은 `sub`(사용자 id), `iat`, `exp`만 담는다 ⑧ 요청의 `rememberMe`(선택, 기본 false)가 true면 AUTH-06 리프레시 토큰을 함께 발급한다 (v0.4) |
| AUTH-03 | 로그아웃한다. | ① 액세스·리프레시 토큰 쿠키가 모두 제거되고(`Max-Age=0`), 리프레시 토큰이 있으면 **서버에서 같은 묶음 전체를 폐기**한다 → **204** ② 로그아웃 후 보호된 API 호출은 401 (쿠키가 지워졌으므로), 폐기된 리프레시 토큰으로 연장하면 401 ③ (v0.4 변경) **로그인 없이도 호출할 수 있고 항상 204** (멱등). 액세스 토큰이 만료된 사용자도 리프레시 토큰을 폐기할 수 있어야 하기 때문 (D-17). CSRF는 필요 |
| AUTH-04 | 보호된 API는 유효한 토큰이 있어야 호출할 수 있다. | ① 토큰 없음/만료/서명 불일치 → 401 `UNAUTHORIZED` ② 인증은 됐지만 권한 없음 → 403 `FORBIDDEN` ③ 토큰은 **쿠키로만** 받는다 (`Authorization` 헤더는 읽지 않음) |
| AUTH-05 | 클라이언트는 현재 로그인 상태를 조회한다. (토큰 쿠키가 HttpOnly라 JS로 읽을 수 없으므로 필요) | ① 로그인 상태면 **200**, 사용자 id와 **마스킹된 표시명(A-1)**만 반환 `{ "id": 1, "displayName": "ab***@example.com" }` ② 이메일 원문, role, password_hash는 포함하지 않음 (DATA-05) ③ 비로그인·토큰 무효 시 401 |
| AUTH-06 | (v0.4) 로그인 상태를 유지한다. 액세스 토큰(1시간)이 만료돼도 다시 로그인하지 않고 연장한다. | ① `rememberMe: true`로 로그인·회원가입하면 리프레시 토큰 쿠키를 추가로 발급한다 (SEC-16) ② `POST /api/auth/refresh`: 유효한 리프레시 토큰이면 **200**, 새 액세스 토큰 쿠키와 **새 리프레시 토큰**(교체)을 발급, 본문은 AUTH-05 형태 ③ 리프레시 토큰은 **한 번만** 쓸 수 있다 (사용 즉시 폐기) ④ **이미 사용한 리프레시 토큰이 다시 오면 탈취로 보고 같은 묶음(family) 전체를 폐기**하고 401 — 공격자와 정상 사용자 중 누가 먼저 썼든 둘 다 다시 로그인해야 한다 ⑤ 만료·폐기·없음·형식 오류는 **401 `UNAUTHORIZED`** + 리프레시 쿠키 삭제 ⑥ 유지 기간은 **최초 로그인 시점부터 A-7(14일)**. 연장해도 늘어나지 않는다(절대 만료) ⑦ 액세스 토큰 없이 호출할 수 있다 (만료된 액세스 토큰 쿠키가 있어도 무시, AUTH-02 ⑥과 같은 이유). CSRF는 필요 ⑧ `rememberMe`가 false·없음이면 지금처럼 액세스 토큰만 발급 |

### 4.2 게시글 (POST)

| ID | 요구사항 | 수용 기준 (AC) |
|---|---|---|
| POST-01 | 회원은 게시글을 작성한다. | ① 제목 1~100자, 본문 1~10,000자 (앞뒤 공백 제거 후). **문자 수는 유니코드 문자(코드 포인트) 기준**(이모지 1개 = 1자), 공백 제거는 유니코드 공백 기준(`strip`), **제거한 값을 저장**한다 (v0.5, D-22) ② 범위 밖·누락·공백만 → **400 `VALIDATION_FAILED`**, `fields`에 `title`/`content` ③ 작성자·작성 시각 자동 기록. 요청에 `authorId` 등 다른 필드가 있어도 무시 ④ (v0.5) 성공 → **201**, 본문은 POST-03 상세와 같은 형태 (D-23) ⑤ 비로그인 → 401 |
| POST-02 | 누구나 게시글 목록을 조회한다. | ① 최신순 정렬 (작성 시각 내림차순, 같으면 id 내림차순) ② 페이지당 20개, 페이지 번호 방식: **`?page=` 0부터, 생략 시 0. 크기는 서버 고정**(크기 파라미터 없음, 보내도 무시) (v0.5, D-21) ③ 삭제된 글은 목록에서 제외 ④ (v0.5 확정) 음수 `page` → **400 `VALIDATION_FAILED`** (`fields: ["page"]`), 숫자가 아니면 **400 `INVALID_REQUEST`**, 마지막 페이지를 넘으면 **200 + 빈 목록** ⑤ (v0.5) 응답 `{ items, page, size, totalElements, totalPages }`, 항목은 `id, title, authorName, createdAt`만 (본문·권한 불리언 없음) |
| POST-03 | 누구나 게시글 상세를 조회한다. | ① 제목, 본문, 작성자 표시명, 작성·수정 시각 반환 → (v0.5) `{ id, title, content, authorName, createdAt, updatedAt, canEdit, canDelete }`. `authorName`은 A-1 마스킹, **`updatedAt`은 수정 전이면 `null`**, 시각은 UTC ISO-8601(`…Z`) (D-23) ② 존재하지 않거나 삭제된 글은 404 `NOT_FOUND` (둘을 구분하지 않음) ③ 요청자 기준으로 서버가 계산한 `canEdit`, `canDelete` 불리언 포함 (비회원은 둘 다 false, 관리자는 타인 글에 대해 `canEdit=false`, `canDelete=true`) ④ (v0.5) 공개 조회 API(목록·상세)에 **만료·변조된 액세스 토큰 쿠키가 함께 오면 401 `UNAUTHORIZED`** — 비회원으로 취급하지 않는다 (D-20) |
| POST-04 | 작성자는 본인 글을 수정한다. | ① 본인 글만 가능, 타인 글은 403 (관리자 포함) ② 검증 규칙은 POST-01과 동일 (제목·본문 **둘 다** 보낸다, 일부 수정 없음) ③ 수정 시각 갱신 ④ 삭제된 글은 404 ⑤ (v0.5) 성공 → **200**, 본문은 POST-03 상세 형태 ⑥ (v0.5) 검사 순서: 401(비로그인) → 400(입력) → 404(없음·삭제됨) → 403(권한) (D-24) |
| POST-05 | 작성자는 본인 글을, 관리자는 모든 글을 삭제한다. | ① 소프트 삭제 (DATA-03): `deleted_at`, `deleted_by`(요청자 id) 기록 → **204** ② 권한 없으면 403 ③ 이미 삭제된 글은 404 (검사 순서는 POST-04 ⑥과 같음) ④ 게시글 삭제 시 해당 글의 댓글도 조회되지 않음 — **(v0.5) 댓글 API가 생기는 댓글 PR에서 검증** (D-25) |

> `canEdit`/`canDelete`는 **화면 표시용 힌트**일 뿐이다. 실제 허용 여부는 수정·삭제 요청 시 서버가 다시 확인한다 (SEC-07).
>
> (v0.5) 관리자 여부는 토큰이 아니라 **매 요청 DB의 role**로 판단한다 (토큰 클레임은 `sub`·`iat`·`exp`뿐, AUTH-02 ⑦). 역할이 바뀌면 다음 요청부터 반영된다.

### 4.3 댓글 (COMMENT)

| ID | 요구사항 | 수용 기준 (AC) |
|---|---|---|
| CMT-01 | 회원은 게시글에 댓글을 작성한다. | ① 내용 1~1,000자 (앞뒤 공백 제거 후). **문자 수는 유니코드 문자(코드 포인트) 기준**이고 공백 제거는 `strip`, **제거한 값을 저장**한다 (POST-01 ①, D-22와 같은 기준) ② 범위 밖·누락·공백만 → **400 `VALIDATION_FAILED`**, `fields: ["content"]` ③ 작성자·작성 시각 자동 기록. 요청에 `authorId`·`postId` 등 다른 필드가 있어도 무시 (댓글이 달리는 글은 **경로의 id로만** 정해진다) ④ 존재하지 않거나 삭제된 게시글이면 **404 `NOT_FOUND`** (둘을 구분하지 않음) ⑤ 단일 계층 (대댓글 없음) ⑥ 성공 → **201**, 본문은 CMT-02의 항목 하나와 같은 형태 (D-27) ⑦ 비로그인 → 401 ⑧ 경로의 `id`가 숫자가 아니면 400 `INVALID_REQUEST` (게시글 API와 같다) ⑨ 검사 순서: 401(비로그인) → 400(입력) → 404(글 없음·삭제됨) (D-29) |
| CMT-02 | 누구나 게시글의 댓글을 조회한다. | ① **별도 API** `GET /api/posts/{id}/comments` (게시글 상세 응답에는 댓글을 넣지 않는다, D-26) ② **작성순(오래된 순)**: 작성 시각 오름차순, 같으면 id 오름차순 ③ 삭제된 댓글은 제외 ④ 응답 `{ "items": [ { id, content, authorName, createdAt, canDelete } ] }`. `authorName`은 A-1 마스킹, 시각은 UTC ISO-8601(`…Z`), `canDelete`는 요청자 기준 서버가 계산한 불리언 (비회원 false, 작성자 true, 관리자는 모든 댓글 true). 이메일 원문·role·`deleted_*`는 포함하지 않음 (DATA-05) ⑤ 글이 없거나 삭제됐으면 **404 `NOT_FOUND`** → **삭제된 글의 댓글은 조회되지 않는다** (POST-05 ④를 이 AC로 검증, D-25) ⑥ 댓글이 없으면 200 + `items: []` ⑦ **만료·변조된 액세스 토큰 쿠키가 함께 오면 401 `UNAUTHORIZED`** (POST-03 ④, D-20과 같다) ⑧ 경로의 `id`가 숫자가 아니면 400 `INVALID_REQUEST` ⑨ 페이지 나누기·개수 상한은 두지 않는다 (D-30, 7장) |
| CMT-03 | 작성자는 본인 댓글을, 관리자는 모든 댓글을 삭제한다. | ① 소프트 삭제 (DATA-03): `deleted_at`, `deleted_by`(요청자 id) 기록 → **204** ② 권한 없으면 403 ③ 이미 삭제된 댓글은 404 ④ **소속 게시글이 삭제된 댓글도 404** (조회할 수 없는 댓글이므로 존재를 알리지 않는다, D-31) ⑤ 검사 순서: 401(비로그인) → 404(없음·삭제됨·글 삭제됨) → 403(권한) (POST-05 ③, D-24와 같다) ⑥ 경로의 `id`가 숫자가 아니면 400 `INVALID_REQUEST` ⑦ 관리자 여부는 토큰이 아니라 **매 요청 DB의 role**로 판단한다 (T-15) |

> `canDelete`는 CMT-02와 같이 **화면 표시용 힌트**일 뿐이다. 실제 허용 여부는 삭제 요청 시 서버가 다시 확인한다 (SEC-07).

### 4.4 관리자 (ADMIN)

| ID | 요구사항 | 수용 기준 (AC) |
|---|---|---|
| ADM-01 | 관리자 계정은 최초 배포 시 시드로 1개 생성된다. | ① 이메일·비밀번호는 환경변수/시크릿(`ADMIN_EMAIL`, `ADMIN_PASSWORD`)으로 주입 (코드·저장소에 평문 금지) ② 이미 존재하면 다시 만들지 않음 (멱등). **같은 이메일의 계정이 이미 있으면 역할·비밀번호를 바꾸지 않고** 건너뛴다 (D-32) ③ 시크릿이 없으면 시드를 건너뛰고 경고 로그 ④ 이메일은 AUTH-01 ⑤⑥(정규화·형식), 비밀번호는 SEC-03 정책을 **그대로** 적용한다. 위반하면 계정을 만들지 않고 건너뛰며 경고 로그 ⑤ 로그(경고 포함)에 비밀번호와 이메일 원문을 남기지 않는다 (SEC-11) ⑥ 시드는 **앱 기동 시** 실행되며, 실패해도 앱 기동은 막지 않는다 ⑦ 만들어진 관리자는 일반 로그인(AUTH-02)으로 로그인하고 `role=ADMIN`이다 |
| ADM-02 | 관리자는 게시글·댓글을 삭제할 수 있다. | POST-05, CMT-03 참조. 별도 관리자 화면 없이 일반 화면의 삭제 버튼 사용 |
| ADM-03 | 관리자 삭제는 추적 가능하다. | 삭제한 사용자 ID와 시각이 기록된다 (DATA-03) |

### 4.5 공통 API 규칙 (v0.3 신설)

**성공 상태코드** (03 문서 H-Q1 확정)

| 동작 | 상태코드 | 해당 API |
|---|---|---|
| 생성 | 201 | 회원가입(본문 있음, v0.4), 게시글 작성, 댓글 작성 |
| 조회·수정·로그인 | 200 | 목록·상세·댓글 조회, 게시글 수정, 로그인, 로그인 연장(`/api/auth/refresh`), 현재 사용자 조회 |
| 본문 없는 처리 | 204 | 로그아웃, 게시글·댓글 삭제, CSRF 토큰 발급(`GET /api/csrf`) |

**오류 응답 형식** — 모든 오류(4xx·5xx)는 같은 JSON 형식을 쓴다.

```json
{ "code": "VALIDATION_FAILED", "message": "입력값을 확인해 주세요.", "fields": ["email"] }
```

| 필드 | 설명 |
|---|---|
| `code` | 기계가 읽는 오류 코드 (아래 표). 클라이언트는 이 값으로 분기한다 |
| `message` | 사용자에게 보여 줄 수 있는 한국어 문장. **입력값·내부 정보(예외명, SQL, 경로)를 담지 않는다** (SEC-10) |
| `fields` | 검증 실패한 필드 이름 목록 (값은 담지 않음). 해당 없으면 빈 배열 |

| code | 상태 | 언제 |
|---|---|---|
| `VALIDATION_FAILED` | 400 | 입력 검증 실패 |
| `INVALID_REQUEST` | 400 | 본문이 JSON이 아니거나 형식이 맞지 않음 |
| `INVALID_CREDENTIALS` | 401 | 로그인 실패 (AUTH-02 ②) |
| `UNAUTHORIZED` | 401 | 토큰 없음·무효 (AUTH-04 ①) |
| `FORBIDDEN` | 403 | 권한 없음 (AUTH-04 ②) |
| `CSRF_INVALID` | 403 | CSRF 토큰 없음·불일치 (SEC-05) |
| `NOT_FOUND` | 404 | 리소스·경로 없음 |
| `METHOD_NOT_ALLOWED` | 405 | 지원하지 않는 HTTP 메서드 |
| `EMAIL_ALREADY_USED` | 409 | 회원가입 이메일 중복 (AUTH-01 ②) |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | JSON이 아닌 Content-Type |
| `INTERNAL_ERROR` | 500 | 그 밖의 서버 오류 |

## 6. 비기능 요구사항

### 6.1 보안 (SEC)

| ID | 요구사항 |
|---|---|
| SEC-01 | 모든 입력은 **서버에서** 검증한다 (클라이언트 검증은 보조). |
| SEC-02 | 비밀번호는 적응형 해시(bcrypt 또는 Argon2)로 저장한다. 평문·가역 암호화 금지. |
| SEC-03 | 비밀번호 정책: **8~64자(유니코드 문자 기준) 그리고 UTF-8 72바이트 이하**. 앞뒤 공백을 제거하지 않는다 (공백도 비밀번호의 일부). 문자 조합 강제 없음. |
| SEC-04 | JWT는 서버 측 비밀키로 서명하고, 비밀키는 환경변수/시크릿으로 관리한다. `alg=none` 등 서명 미검증 토큰은 거부한다. **키는 Base64로 인코딩한 256비트(32바이트) 이상 무작위 값**이며, 없거나 짧으면 앱이 기동하지 않는다. |
| SEC-05 | JWT는 `HttpOnly; Secure; SameSite` 쿠키로 전달한다 (localStorage 저장 금지 → XSS로 인한 토큰 탈취 완화). 쿠키 사용에 따른 **CSRF 방어**를 적용한다. |
| SEC-06 | 액세스 토큰 유효기간은 짧게(예: 1시간) 둔다. 리프레시 토큰은 MVP 제외 → 만료 시 재로그인. |
| SEC-07 | 인가는 서버에서 매 요청마다 확인한다. 리소스 소유자 확인 누락(IDOR)이 없도록 수정·삭제 시 `author_id` 또는 ADMIN 역할을 검증한다. |
| SEC-08 | 게시글·댓글은 **일반 텍스트**로만 저장·표시하며 출력 시 이스케이프한다 (HTML/마크다운 렌더링 없음 → 저장형 XSS 방지). |
| SEC-09 | DB 접근은 파라미터 바인딩만 사용한다 (SQL 인젝션 방지). |
| SEC-10 | 오류 응답에 스택트레이스, SQL, 내부 경로를 노출하지 않는다. |
| SEC-11 | 로그에 비밀번호, 토큰, 시크릿을 기록하지 않는다. |
| SEC-12 | 운영 환경은 HTTPS만 허용한다. |
| SEC-13 | CORS는 허용 출처를 명시적으로 지정한다 (와일드카드 + 자격증명 조합 금지). |
| SEC-14 | 기본 보안 헤더를 설정한다 (CSP, X-Content-Type-Options, X-Frame-Options 또는 frame-ancestors 등). |
| SEC-15 | 저장소에 시크릿을 커밋하지 않는다. CI에서 시크릿 스캔과 의존성 취약점 스캔을 수행한다. |
| SEC-16 | (v0.4) 리프레시 토큰은 **256비트 암호학적 난수**(JWT 아님)이고, DB에는 **SHA-256 해시만** 저장한다. 쿠키는 `HttpOnly; Secure; SameSite=Strict; Path=/api/auth`로 인증 API에만 전송되게 한다. 1회용으로 교체하고(AUTH-06 ③), 재사용이 감지되면 묶음 전체를 폐기한다(④). |

### 6.2 테스트·하네스 (TST)

| ID | 요구사항 |
|---|---|
| TST-01 | 4장의 모든 AC는 자동화된 테스트로 검증된다. 기능 구현 전에 테스트를 먼저 작성한다. |
| TST-02 | 3.1 권한 매트릭스의 모든 칸(허용/거부)에 대응하는 인가 테스트가 존재한다. `canEdit`/`canDelete` 값도 역할별로 검증한다. |
| TST-03 | 보안 요구사항 중 테스트 가능한 항목(SEC-05, 07, 08, 10 등)은 회귀 테스트로 유지한다. |
| TST-04 | 테스트는 **Docker만 있으면** 로컬과 CI에서 동일한 명령으로 실행된다. 테스트 DB는 테스트 실행 시 컨테이너로 자동 기동되는 격리된 DB를 사용하며, 공유 DB·외부 서비스에 의존하지 않는다. |
| TST-05 | MVP의 AC는 API 통합 테스트로 검증한다. 브라우저 E2E 테스트는 MVP에서 제외한다 (7장). |
